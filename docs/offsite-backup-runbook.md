# Offsite-копия бэкапов: подготовка и включение

**Состояние на 27.10.2026:** не включено. Нужны бакет и ключ владельца; аккаунты и ключи агент не создаёт и не вводит.
Код готов: `scripts/pg-backup.sh` (шаг О-1) заливает оба файла в S3-совместимое хранилище, сверяет размер объекта с локальным файлом и сообщает результат в Telegram. Пока `OFFSITE_S3_BUCKET` пуст, шаг пропускается.

## Зачем

Дампы лежат на том же диске, что и база (`/opt/rosstat/backups`, диск хоста 88 % при 9,8 ГБ свободных на 27.10). Копия на Mac ненадёжна: ноутбук с закрытой крышкой спит ([причина и исправление](workflow.md#доставка-существующего-backup-на-mac)), к тому же она одна. Offsite нужен на случай потери сервера или диска.

## Решения владельца до начала

1. **Провайдер и страна.** В дампе лежат email и хэши паролей пользователей, поэтому хранилище разумно выбрать в России (Яндекс Object Storage, Selectel, VK Cloud и т. п.) из-за 152-ФЗ. Если нужен зарубежный S3, сначала решить вопрос о шифровании на стороне клиента (последний раздел). Код от провайдера не зависит: нужны только endpoint и ключи.
2. **Срок хранения.** Предлагается 30 суток правилом жизненного цикла бакета (скрипт на сервере объекты не удаляет). Объём: один дамп около 0,55 ГБ и растёт примерно на 4–5 МБ в сутки, 30 копий — порядка 17 ГБ.
3. **Кто платит и под каким аккаунтом.** Создаёт владелец сам.

## Что делает владелец (консоль провайдера)

1. Создать **закрытый** бакет (публичный доступ выключен), например `fe-pg-backups`, регион как у сервера.
2. Правило жизненного цикла: удалять объекты старше 30 суток; незавершённые multipart-загрузки — через 1 сутки.
3. Сервисный аккаунт только на этот бакет с правами «загрузка и чтение/список» (в Яндекс Object Storage — `storage.uploader` плюс `storage.viewer`; удаление не нужно). Для restore-учений — отдельная роль на чтение у того, кто восстанавливает.
4. Статический ключ доступа этого аккаунта. **Ключ не присылать в чат и не класть в Git**: он вводится на сервере вручную (шаги ниже).

## Что готово на стороне хоста (не применялось)

Все шаги вручную по SSH, по одному, с проверкой. Ничего из этого не запускалось на проде.

```bash
# 1. aws cli. В Ubuntu 24.04 пакета awscli в apt нет. Сначала архитектура:
uname -m                       # x86_64 -> awscli-exe-linux-x86_64.zip, aarch64 -> ...-aarch64.zip
cd /root && mkdir -p awscli-install && cd awscli-install
curl -fsSLo awscliv2.zip https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip
unzip -q awscliv2.zip && ./aws/install     # ставит в /usr/local/bin/aws
aws --version
cd /root && rm -rf awscli-install

# 2. Ключ в профиль root (cron pg-backup идёт от root). Ввести вручную; файл только для root.
aws configure set aws_access_key_id     '<ключ>'  # владелец вводит сам
aws configure set aws_secret_access_key '<секрет>'
aws configure set region ru-central1
chmod 600 /root/.aws/credentials

# 3. Проверка доступа МАЛЕНЬКИМ файлом, без запуска дампа.
EP=https://storage.yandexcloud.net            # endpoint провайдера
echo "probe $(date -u +%FT%TZ)" | aws s3 cp - s3://fe-pg-backups/pg-backups/offsite-probe.txt --endpoint-url "$EP"   # со stdin, файла на диске нет
aws s3 ls s3://fe-pg-backups/pg-backups/offsite-probe.txt --endpoint-url "$EP"
aws s3 rm s3://fe-pg-backups/pg-backups/offsite-probe.txt --endpoint-url "$EP"   # нужна роль с удалением; иначе объект уйдёт по правилу срока

# 4. Включить шаг: две строки в /opt/rosstat/.env (скрипт читает их как данные, не source).
#    OFFSITE_S3_BUCKET=s3://fe-pg-backups/pg-backups
#    OFFSITE_S3_ENDPOINT=https://storage.yandexcloud.net
```

Ни ключ, ни секрет не должны попасть в `.env`: он читается compose и может уйти в контейнеры. Профиль `/root/.aws/credentials` читает только `aws` на хосте.

## Проверка после включения

- **Первый боевой прогон** — ближайший cron 04:00 UTC или `deploy.sh`. В Telegram должно прийти `🟢 pg-backup ok: … offsite ok`. Если пришло `🟡 … offsite НЕ выполнен: …`, локальный дамп всё равно создан, деплой не остановлен; причину смотреть в `/var/log/pg-backup.log` (строки `WARN` и `Offsite size mismatch`).
- **Ручная сверка:** `aws s3 ls s3://fe-pg-backups/pg-backups/ --endpoint-url "$EP"` показывает оба файла с теми же размерами, что в `/opt/rosstat/backups`.
- **Restore-учение из offsite** (на Mac, не на проде): скачать объект в пустую папку, сверить SHA-256 с серверным `sha256sum`, затем `pg_restore --list` и изолированное восстановление по [workflow](workflow.md#git-и-окружения). Факт `aws s3 cp` без восстановления копией не считается ([enterprise_resilience](enterprise_resilience.md#восстановление-и-наблюдаемость)).

## Откат

Убрать две строки из `/opt/rosstat/.env`: шаг снова пропускается. Профиль и объекты в бакете можно не трогать; ключ при сомнении отозвать в консоли провайдера.

## Что изменено в коде (27.10.2026)

- Раньше при заданном бакете без `aws` скрипт слал жёлтое сообщение, а затем всё равно зелёное «ok»; сбой `aws s3 cp` ронял весь скрипт (и `deploy.sh` вставал). Теперь: сбой offsite не роняет скрипт, но вместо зелёного сообщения уходит жёлтое с причиной; после заливки размер объекта сверяется с локальным. Тесты: `backend/tests/test_pg_backup_offsite.py`.
- Скрипт не удаляет объекты в бакете: срок хранения задаёт правило бакета.

## Пределы

- Размер объекта совпадает, но SHA-256 объекта скрипт не сравнивает (для мультичастных загрузок ETag не равен SHA-256); целостность подтверждает restore-учение.
- Шифрование на стороне клиента не включено. Если выбран зарубежный провайдер или нужна защита от доступа администраторов бакета, перед заливкой шифровать (`age -r <публичный ключ>`), а приватный ключ хранить вне сервера и вне бакета; это отдельное решение, в скрипт не заложено.
- Независимые бэкапы самого хостера (Timeweb) не проверялись.
