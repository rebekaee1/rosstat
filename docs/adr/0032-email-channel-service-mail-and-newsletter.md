# ADR-0032: Почта сайта — служебные письма и рассылка

**Status:** Accepted 14.11.2026 по слову владельца («надо подумать насчет рассылок… будем тестировать на почту отправлять rebeka.ee@yandex.ru… заняться всеми моментами, которые только могут быть в рассылке и не только в ней»). Код выключен флагом `RUSTATS_MAIL_ENABLED=false` и закрыт списком допуска; **не выпущено**; живое письмо не отправлялось: нет пароля SMTP (см. «Порядок включения»).
**Date:** 2026-11-14.
**Part of:** [`../data-contracts.md`](../data-contracts.md#почта-сайта--2026-11-14), [`../workflow.md`](../workflow.md#почта-сайта-adr-0032).
**Related:** [ADR-0007](0007-identity-user-accounts.md) (аккаунты, журнал согласий append-only, 152-ФЗ), [ADR-0010](0010-analytics-contour-identity-goals-marts-olap.md) (метки utm), [ADR-0019](0019-personal-cabinet-behind-flag.md) (кабинет, переключатель рассылки), [ADR-0018](0018-crystal-without-borders-design-system.md) (вид писем).
**Code anchors:** `backend/app/services/mail/` (`tokens.py`, `templates.py`, `transport.py`, `service.py`, `audience.py`, `campaign.py`, `account.py`), `backend/app/api/mail.py`, `backend/app/api/auth.py` (`/email/verify`, `/email/verify/resend`, `/password/forgot`, `/password/reset`, хуки в `register` и `set-password`), `backend/app/models.py::MailMessage`, Alembic `20261114_mail_outbox`, `backend/scripts/mail.py`, `frontend/src/pages/AccountMail.jsx`, `frontend/nginx.conf` (маршрут `/account/…`), `backend/tests/test_mail.py`, `frontend/src/pages/AccountMail.component.test.jsx`.

## Контекст (замер 14.11.2026)

- Домен `forecasteconomy.com` на DNS nic.ru, почта — Яндекс 360: MX `mx.yandex.net`, SPF `v=spf1 redirect=_spf.yandex.net`, DKIM селектор `mail` (RSA 1024, `t=s`), DMARC `v=DMARC1; p=none; rua=mailto:dmarc@forecasteconomy.com` (добавлен 14.11).
- В коде отправки писем не было. Были: галочка согласия на рассылку (`Consent kind="newsletter"`, по умолчанию включена — решение владельца 05.10, не менять), переключатель в кабинете, темы рассылки только хранились. «Забыли пароль?» открывал письмо владельцу (`mailto:info@…`); адрес входа по паролю никогда не подтверждался.
- Аккаунтов 194, все активные. Адрес входа по паролю у 111 (подтверждённых 0), Яндекс 42 (адрес у 40, подтверждён провайдером), Google 8, VK 33 (адреса нет ни у одного). Без адреса 35 аккаунтов. Подписаны на рассылку сейчас 122. Почтовые сервисы: gmail.com 54, yandex.ru 53, mail.ru 28, list.ru/bk.ru по 3. Язык регистрации известен у 64 (ru 56, en 8) — остальные регистрировались до записи `user_signups`.
- Лимиты Яндекс 360 по официальной справке не найдены; сторонние источники: ~300 получателей в сутки по SMTP у обычной Почты, ~3000 в сутки с ящика организации; правила запрещают массовые рассылки через обычный ящик; для рассылок у Яндекса есть модуль «Рассылки» в Яндекс 360 для бизнеса (1500 писем в месяц на младшем тарифе) и Yandex Cloud Postbox. При превышении блокируется отправка с ящика на сутки.

## Решение

1. **Один путь отправки — SMTP.** Транспорт не знает провайдера: Яндекс 360 (`smtp.yandex.ru:465`, пароль приложения) сейчас; Yandex Cloud Postbox или другой SMTP-сервис — сменой хоста, пользователя и пароля в `.env`. From = ящик входа (иначе Яндекс отклоняет письмо), Reply-To = `info@forecasteconomy.com`. DKIM ставит почтовый сервис домена.
2. **Три защиты от случайной отправки людям.** `RUSTATS_MAIL_ENABLED=false` (по умолчанию) — ничего не уходит в сеть; список допуска `RUSTATS_MAIL_ALLOWLIST` (по умолчанию `rebeka.ee@yandex.ru`) действует, пока `RUSTATS_MAIL_ALLOW_ALL_RECIPIENTS=false`, и для служебных писем тоже; выпуск рассылки людям — только `scripts/mail.py campaign … --send` и только при снятом списке. Остальные адреса получают статус `blocked` в журнале.
3. **Журнал `mail_outbox`.** Строка на каждое письмо до сети: вид, выпуск, человек, адрес, язык, тема, статус (`queued/sent/failed/blocked/disabled`), попытки, короткий код ошибки, Message-ID. Тело не хранится. Уникальность (выпуск, человек) — повторный запуск выпуска продолжает с места остановки и не шлёт дважды. Адрес — ПДн: удаляется с аккаунтом, виден в выгрузке «Мои данные».
4. **Подписанные ссылки без входа на сайт.** HMAC-SHA256 на `RUSTATS_MAIL_TOKEN_SECRET`, назначение в подписи: `unsub` (без срока), `verify` (7 суток, привязан к адресу), `reset` (1 час, привязан к отпечатку хэша пароля — одноразовый). Без секрета письма со ссылками не формируются.
5. **Служебные письма.**
   - Подтверждение адреса: уходит после регистрации по паролю и после `set-password` (если провайдер входа этот адрес ещё не подтвердил); ссылка `/account/verify-email?t=…`; в кабинете — плашка «Подтвердите почту» с повтором письма (3 в час).
   - Сброс пароля: `/account/forgot-password` → письмо → `/account/reset-password?t=…`. Ответ на запрос одинаков для любого адреса; лимиты 3 письма в час на адрес и 10 запросов в час с IP. После смены пароля закрываются все сессии, адрес считается подтверждённым, счётчик неудачных входов сбрасывается.
   - Письма уходят фоновой задачей после ответа; сбой почты не роняет регистрацию.
6. **Рассылка.**
   - Получатели: последняя запись журнала согласий — `newsletter` (тот же отбор, что в счётчике подписчиков), аккаунт активен; адрес: подтверждённый по паролю → подтверждённый провайдером → неподтверждённый (по умолчанию неподтверждённые пропускаются, `--include-unverified` — явное решение). Язык письма: язык регистрации → страна регистрации → язык профиля провайдера → домен почты → русский.
   - Выпуск — JSON-файл (тема, заголовок, вступление, блоки с числом, кнопка; по языкам). На свои ссылки добавляются `utm_source=email&utm_medium=newsletter&utm_campaign=<ключ>`.
   - Не больше `RUSTATS_MAIL_CAMPAIGN_MAX_PER_RUN` (250) писем за запуск, пауза 4 с; ответ сервера о лимите или спаме останавливает выпуск; перед каждым письмом заново проверяется подписка.
   - Отписка в одно нажатие: заголовки `List-Unsubscribe` (HTTPS + mailto) и `List-Unsubscribe-Post: List-Unsubscribe=One-Click` (RFC 8058) + ссылка в подвале на `/account/unsubscribe?t=…`. Страница отписывает при открытии (сканеры ссылок JavaScript не выполняют), GET API ничего не меняет, есть «Подписаться снова». Отписка — новая запись `newsletter_revoked` в журнале согласий.
7. **Вид письма** — по принципам владельца: холодный светлый фон со светом, плита письма отделена светлотой и тенью без рамок, знак «Forecast Economy» текстом и одна тонкая золотая линия, кнопка глубокого синего, без картинок (не блокируются почтой, не теряют резкости), простой текст рядом с HTML. В подвале — почему пришло письмо, отписка, кабинет, адрес для вопросов и реквизиты оператора.
8. **Ссылки на страницы писем** под `/account/…` (не новый корень: иначе пришлось бы расширять список зарезервированных слагов стран); nginx отдаёт оболочку с `noindex` и `Referrer-Policy: no-referrer`; страница сразу убирает токен из адресной строки (история браузера, события аналитики с полным URL).

## Последствия

- **Плюс:** люди могут сами вернуть пароль; адреса начинают подтверждаться — рассылка уходит на живые адреса, меньше отказов и жалоб; отписка соответствует требованиям Gmail и Яндекса; повторный запуск выпуска безопасен.
- **Цена:** новая таблица и миграция; служебные письма зависят от одного ящика Яндекс 360 — при блокировке ящика за рассылку перестанут уходить и сбросы паролей (поэтому рассылку лучше вести через отдельный сервис, см. «Не решено»).
- **Не решено / неизвестно (14.11.2026):** живая доставка, заголовки SPF/DKIM/DMARC в полученном письме и попадание во «Входящие» не проверены — нет пароля SMTP; точные лимиты Яндекс 360 для этого тарифа не подтверждены официальной справкой; асинхронные отказы (адрес не существует — письмо-отказ приходит в ящик отправителя позже) не разбираются автоматически; письма на `info@…?subject=unsubscribe` обрабатываются руками; содержание выпусков владелец обсуждает с партнёром; юридическая оценка рассылки по ранее предотмеченной галочке не делалась (решение владельца 05.10 в силе).

## Порядок включения

1. Миграция `20261114_mail_outbox` (только добавление таблицы) — штатным выпуском.
2. Владелец: ящик-отправитель и пароль приложения (шаги — [workflow](../workflow.md#почта-сайта-adr-0032)); в `/opt/rosstat/.env` — `RUSTATS_MAIL_SMTP_USER`, `RUSTATS_MAIL_SMTP_PASSWORD`, `RUSTATS_MAIL_TOKEN_SECRET` (`openssl rand -hex 32`), `RUSTATS_MAIL_ENABLED=true`; `docker compose up -d --force-recreate backend`.
3. `python /app/scripts/mail.py check` → `test --to rebeka.ee@yandex.ru` → заголовки `Authentication-Results` в полученном письме (spf=pass, dkim=pass, dmarc=pass).
4. Снять список допуска (`RUSTATS_MAIL_ALLOW_ALL_RECIPIENTS=true`) — только по команде владельца: с этого момента подтверждения и сбросы паролей уходят людям.
5. Выпуск рассылки людям — отдельной командой владельца: `campaign issue.json` (сухой прогон) → `--test-to` → `--send`.

## Дополнение 14.11.2026: решения координатора 1–7

1. **Отдельный сервис для писем потоком** — направление утверждено, выбор и оплата за владельцем. Второй профиль SMTP `RUSTATS_MAIL_BULK_SMTP_*` (`transport.profile_for`): рассылка и сводка «колокольчика» идут через него, служебные — всегда через основной ящик. Сравнение Postbox и «Рассылок» Яндекс 360 — [workflow](../workflow.md#почта-сайта-adr-0032).

3. **Разбор отказов по IMAP** (`services/mail/bounces.py`, флаг `RUSTATS_MAIL_BOUNCE_POLL_ENABLED`): только чтение ящика; постоянный отказ или жалоба → `mail_suppressions` (новая таблица в той же миграции), строка журнала → `bounced`; жалоба снимает подписку. Письма на адреса из стоп-листа не уходят (`suppressed`). У Postbox отказы приходят событиями Data Streams — этот разбор их не видит.
4. **DMARC и DKIM** — пересмотр 05.12.2026 с критериями ([backlog](../backlog.md#dmarc-dkim-review-2026-12-05)).
5. **Подсказка входа:** «Забыли пароль?» для адреса без пароля, но с подтверждённым входом через провайдера — письмо `oauth_hint` («вы входите через Яндекс ID / Google / VK ID»), ответ запросу прежний.
6. **Письма «колокольчика»** (`services/mail/watch_digest.py`, флаг `RUSTATS_MAIL_WATCH_DIGEST_ENABLED`, по умолчанию выкл.): одна сводка в день (ключ `watch-ГГГГ-ММ-ДД`), только подтверждённые адреса, новое = дата ряда позже `last_seen_date` и `last_notified_date`; своя отписка — назначение ссылки `unsub_watch`, журнал согласий `watch_mail` / `watch_mail_revoked` (без записи письма включены: человек сам нажал «Следить»). Рассылка от неё не зависит.
7. **Админ-BI:** вкладка «Почта», `GET /admin/bi/mail` — письма по видам и статусам, по дням, выпуски, подписчики, подтверждённые адреса, отписки, стоп-лист; без адресов.

- Поля языка `masthead` (строка выпуска над заголовком) и `signoff` (подпись; если она же стоит в конце `outro`, оттуда убирается); абзацы `intro`/`outro` по пустой строке; прехедер без явного поля — начало вступления по границе слова с многоточием.
- На телефоне крупное число блока встаёт под заголовок: копия под заголовком скрыта встроенным стилем и открывается медиазапросом, поэтому почта без медиазапросов показывает число один раз.
- Яндекс Почта рисует `font-weight:650` обычным начертанием — в письмах только 400/600/700.
- Файлы по языкам с разными ключами: `scripts/mail.py campaign issue-ru.json issue-en.json --key fe-weekly-01 [--test-to … --no-db]`.

**Выпуск на получателя (14.11.2026, решение владельца «чтобы все индивидуально получали»).** `campaign.run(…, per_recipient=builder)`: `builder(db, получатель, выпуск)` возвращает содержимое на языке получателя — `Digest`, словарь языка в формате файла выпуска или `None` (пропуск, статус `no_personal_content`). Ключ выпуска, уникальность (выпуск, человек), лимит за запуск, остановка по лимиту сервера и повторная проверка подписки — общие. Ссылки блоков получают `utm_content=b<номер>-<тип>`. Профиль интересов и сборку персонального выпуска делает отдельный агент «персонализация». С персональными выпусками каждое письмо — отдельная отправка, поэтому отдельный сервис для писем потоком (профиль `bulk`, сравнение — [workflow](../workflow.md#почта-сайта-adr-0032)) становится обязательным перед отправкой людям.

## Дополнение 14.11.2026 (ночь): тёмная тема и стык с персонализацией

- **Тёмная тема.** Письмо объявлено только светлым (`<meta name="color-scheme" content="only light">`, `color-scheme: light only`): Apple Mail, iOS и браузеры с автотёмной темой его не перекрашивают. Outlook в тёмной теме помечает элементы `data-ogsc/ogsb` — правила держат сапфировую шапку и белый знак. Проверено в Chrome: обычный вид, принудительная автотёмная тема (без изменений), полная инверсия как в Gmail iOS (знак тёмным на светлой шапке, читается). Знак картинкой пробовали и отказались: при полной инверсии он остаётся белым и пропадает на перекрашенной шапке, а текст инвертируется вместе с фоном. Тёмная тема ящика владельца не включалась (его настройка).
- **Стык с агентом персонализации** (формат утвердил координатор): поле блока `why` (строка «почему этот блок вам» под источником), блок `section` (заголовок раздела без подложки), поле выпуска `personal_note` (подвал) и ссылка «Письма без персональной подборки» — назначение ссылки `unpers`, та же страница `/account/unsubscribe` (список `personal`). Запись — через `app.services.personalization.set_mail_personalization`, если агент её дал, иначе журнал согласий `mail_personal` / `mail_personal_revoked` (по умолчанию подборка включена). `campaign.DEFER` — «отложить» (тихие часы): не пропуск, строки журнала нет, следующий запуск попробует снова. `run(…, count_personal=True)` в сухом прогоне считает покрытие (`personal_ready` / `no_personal_content` / `deferred`). Вкладка «Почта» ждёт `block_effect_summary` агента персонализации («Эффект блоков персонального выпуска»).

## Дополнение 17.11.2026: отказ «похоже на спам» — признак письма, а не лимит ящика

**Основание.** Первый выпуск `fe-weekly-01`, 17.11.2026: Яндекс (`info@`, Яндекс 360) после 12 одинаковых писем отклонил ещё три тем же ответом `554 5.7.1 Message rejected under suspicion of SPAM`; личные письма с тем же верхом принимал. Прежний код склеивал «спам» и «лимит» в один признак `limit` и по первому такому отказу останавливал весь выпуск — один неудачный получатель обрывал рассылку остальным. Коммит `1178244b`.

**Решение.**
- `transport.SendError` получил признак `spam` (слово `spam` в ответе сервера). `spam` включает `limit` (старое поведение для вызывающих сохраняется); код ошибки в журнале — `smtp_<код>:spam` (раньше `smtp_554:limit`); остальные лимиты — `…:limit`, прочие отказы — `…:rejected`.
- Точный текст ответа сервера (до 300 знаков, адреса заменены на `<адрес>`) пишется в журнал backend строкой `smtp refused code=… text=…`: по одному коду 554 лимит от подозрения в спаме не различить. В `mail_outbox.error` по-прежнему только короткий код без адресов.
- `campaign.run`: письмо с отказом `spam` помечается в `mail_outbox` (статус по правилам `service.attempt`), в отчёте это `statuses["spam_rejected"]`, выпуск делает паузу и идёт дальше. Два отказа подряд (`SPAM_STREAK_STOP = 2`) или любой другой отказ с `limit` — остановка `stopped = "server_limit:<код>"`. Удачная отправка сбрасывает счётчик.
- При следующем запуске того же выпуска строка с `error`, оканчивающимся на `:spam`, не повторяется: `statuses["spam_rejected_before"]`. Повтор по такому адресу вредил бы репутации ящика; письмо повторно собирают только по решению владельца (смена тела, снятие пометки).
- Уведомление бота (`funnel.format_sent_notice`, ADR-0034) называет новые состояния: «почтовый сервер счёл письмо спамом» (`spam_rejected`) и «сервер счёл спамом раньше, повтора нет» (`spam_rejected_before`).

**Причина отказов** устранена на стороне содержания письма, а не транспорта: ADR-0033, дополнение 17.11.2026 (блок «Было и стало», одинаковых писем нет). Темп отправки в выпуске — одно письмо в минуту (`RUSTATS_MAIL_CAMPAIGN_PAUSE_SECONDS=60`), порядок волн и опыт — `docs/newsletter-playbook.md`, раздел «Как отправлять». Итог выпуска: принято почтой 107 из 108, один возврат `5.1.1`.

**Не закрыто.** Различение «спам» и «лимит» построено на тексте ответа (`spam` в нижнем регистре); другой провайдер может назвать то же иначе. Тест: `backend/tests/test_mail.py` (два новых).
