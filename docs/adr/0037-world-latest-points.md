# ADR-0037: Последние две точки мировых рядов — узкая копия для каталога страны

**Status:** Accepted 19.11.2026 по слову владельца («давай и 3 вопрос тоже сделаем»: медленный холодный каталог страны). Ветка `p19/16-latest-points`, **не выпущено**; флаг выключен по умолчанию. На боевом только чтение.
**Date:** 2026-11-19.
**Related:** [ADR-0036](0036-search-index.md) (тот же приём — маленькая копия того, что читается при каждом запросе), [надёжность](../enterprise_resilience.md#world-latest-points-2026-11-19), п.7 [`slow-world-api`](../enterprise_resilience.md#slow-world-api-2026-11-19) (механизм каталога), п.15 [`points-autovacuum`](../enterprise_resilience.md#points-autovacuum-2026-11-19), [data-contracts](../data-contracts.md#world-latest-points-2026-11-19), [выпуск](../workflow.md#world-latest-points-release-2026-11-19).
**Code anchors:** `backend/app/services/world_latest_points.py`, `backend/app/api/world.py::_country_recent_points`, `backend/app/models.py` (`WorldLatestPoint`, `WorldLatestPointsState`), Alembic `20261119_world_latest_points`, загрузчики `world_national_ingest.refresh_indicator_extent`, `world_imf_ingest`, `world_pop_ingest`, `scripts/load-world-eurostat.py::refresh_indicator_extent`, `backend/app/main.py` (задача `world_latest_points`), `backend/app/config.py` (`world_latest_points_*`), `backend/tests/test_world_latest_points.py`.

## Контекст

Каталог страны (`GET /world/countries/{slug}`, страница страны) на холодном кэше читает две последние точки каждого
опубликованного ряда страны. У европейских стран 7,8–8,8 тыс. рядов (Испания 8 768, Германия 8 568). Значение точки
лежит только в строке `world_data_points` (16,5 млн строк, 889 МБ + индексы 1 ГБ при `shared_buffers` 896 МБ), поэтому
каждый ряд — около двух случайных чтений с диска. Замеры на боевом 19.11.2026 (только чтение):

| Что | Рядов | Чтений с диска | Время |
|---|---|---|---|
| Последние 2 точки, Германия (п.15) | 500 | 938 | 1,87 с |
| Последние 2 точки, Косово (`EXPLAIN ANALYZE`) | 640 | 499 | 1,42 с (2,8 мс на чтение) |
| Те же точки диапазоном рядов (обход копии) | 1 540 | 3 129 | 18,4 с (5,8 мс на чтение, диск занят) |
| Строки рядов Косово (`world_indicators`) | 640 | 418 | 0,57 с |

По 2,2–2,4 мс на ряд у Германии это ~20 с одних последних точек; п.7 разбил их на части по 2 000 рядов, чтобы каждая
уложилась в предел запроса 30 с, но сумма осталась. Очистка таблицы (п.15) карту видимости освежает, а чтение строки
таблицы ради значения не убирает.

## Решение

Таблица `world_latest_points` — одна строка на ряд: дата и значение последней и предпоследней точки и
`has_nonzero` (есть ненулевая точка — то же условие `value <> 0`, что `_ids_with_nonzero_signal`). Индекс
`ix_world_latest_points_country (country_id) INCLUDE (…все столбцы…)`: строки страны читаются только из индекса,
у Германии это около 50 страниц подряд (8,5 тыс. записей по ~48 байт).

**Ответ каталога тот же.** Копия хранит ровно то, что давал `latest_world_point_series(limit=2)`, и множество рядов с
ненулевой точкой; значения — тот же `Numeric(20,6)`, перевод во float тот же. Рядов, которых в копии нет, читатель не
угадывает: их последние точки читаются из таблицы точек частями, как раньше (`_country_recent_points`). Тесты
сравнивают весь ответ каталога с копией и без неё: после обхода, после правки загрузчиком, без части строк.

**Свежесть.**

1. **Загрузчики** — после записи точек ряда, там же, где пересчитывается охват ряда (`points_count`,
   `history_start/end`), вызывают `sync_latest_points(db, [id])`. Строка копии меняется в той же транзакции, что
   и точки: откат загрузки откатывает и её, окна устаревания нет. Пишут, только если копия заведена (есть строка
   `world_latest_points_state`; память процесса 60 с), — независимо от флага чтения. Сбой записи в копию загрузку
   не роняет (savepoint): строки этих рядов удаляются, каталог читает их точки по-старому, обход восстановит.
2. **Обход** (`sweep`) — опубликованные ряды страна за страной, частями по `world_latest_points_chunk` (1 000) рядов,
   каждая часть — своя транзакция с пределом запроса 120 с. Первый полный проход заполняет копию; затем повтор раз в
   `world_latest_points_resweep_days` (7) суток чинит то, что прошло мимо загрузчиков (ручной SQL, удалённые ряды).
   Строку, где ничего не изменилось, не переписывает. Часть берёт `pg_try_advisory_xact_lock` (исключительную, без
   ожидания), загрузчик — `pg_advisory_xact_lock_shared`: обход не перезапишет строку старым значением, пока загрузка
   не закрыла транзакцию, и не встаёт в очередь перед загрузками (занято — часть в следующий запуск). Задача
   планировщика — раз в 10 мин в часы `world_latest_points_hours` (МСК, по умолчанию `4,8-21`: вне окон ETL
   23:10–03:10 и 05:30–07:30), до 6 частей и 240 с за запуск. Первое заполнение быстрее — командой
   `python -m app.services.world_latest_points` ([выпуск](../workflow.md#world-latest-points-release-2026-11-19)).
3. **Читатель** берёт копию, только если флаг `world_latest_points_enabled` включён и первый полный проход закончен
   (`filled_at`). Обход начинается не раньше чем через 2 минуты после заведения копии: к первой части все загрузчики
   уже видят строку состояния.

## Почему не другое

- **Триггер на `world_data_points`.** Самая точная свежесть, но каждая загрузка платит за него невидимо, сбой триггера
  роняет загрузку, а выключить его флагом нельзя. Загрузчиков, пишущих точки, четыре, и у всех уже есть общий шаг
  «пересчитать охват ряда» — туда и встала запись копии.
- **Только обновление при сдвиге поколения `world-catalog`.** Евростат сдвигает его, только когда меняется состав
  каталога; новые значения без смены состава в копию бы не попали.
- **Полная пересборка одним запросом** (как поисковый индекс, ADR-0036). Нужны все 16,5 млн точек в порядке
  (ряд, дата): сортировка с временными файлами или ~700 тыс. случайных чтений одним запросом на десятки минут.
  Частями с курсором — те же чтения, но короткими транзакциями и вне ETL.
- **Две копии a/b с переключением.** Нужно для поиска, где копия собирается целиком. Здесь строки правятся на месте
  по одной, читатель видит согласованные строки и так.
- **Колонки «последние точки» в `world_indicators`.** Широкая таблица (2 КБ строка, 700 МБ), каталог её и так читает;
  правка каждой новой точки переписывала бы широкую строку.

## Последствия

- 2 новые таблицы. Оценка объёма: 281 613 опубликованных рядов (боевой 19.11) плюс неопубликованные, которые трогают
  загрузчики; до 361 075 строк × ~70 байт при `fillfactor` 80 ≈ 25–30 МБ таблица + ~20 МБ покрывающий индекс + ~8 МБ
  первичный ключ. Не замерено (таблицы нет на боевом).
- Каталог страны с копией не читает `world_data_points` для последних точек; остаются: строки рядов страны из
  `world_indicators` (Косово 0,9 мс на ряд → Германия ~7–8 с холодно, оценка), «Главное» (14 точек у ~10 рядов),
  число цен (13 точек у 3 рядов), Python и JSON (п.7: < 3 с у Боснии). Холодный каталог Германии — оценка ~10–13 с
  вместо ~30 с. Следующий шаг к единицам секунд — строки рядов из копии поискового индекса (`search_world_a/b`) или
  укладка `world_indicators` по стране (enterprise_resilience, 13.11).
- Загрузчики делают на ряд ещё 3 запроса по только что записанным страницам (последние 2 точки, ненулевая точка при
  нулевом хвосте, запись строки) и берут разделяемую рекомендательную блокировку.
- Рейтинги и главная мира этот запрос не используют (рейтинги — последняя точка каждого года по понятию; главная —
  счётчик `world_country_listed_counts`), их копия не меняет.

## Откат

`RUSTATS_WORLD_LATEST_POINTS_ENABLED=false` в backend — каталог сразу читает таблицу точек; в scheduler — обход не
регистрируется. Загрузчики продолжают вести копию, пока есть строка состояния: остановить —
`DELETE FROM world_latest_points_state;` (через минуту памяти процесса). `alembic downgrade 20261119_points_autovacuum`
удаляет обе таблицы; запись в пропавшую таблицу загрузку не роняет.
