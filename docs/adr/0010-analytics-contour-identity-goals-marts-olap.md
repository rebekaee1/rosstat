# ADR-0010 — Аналитический контур: идентичность, цели, marts, OLAP

**Status:** Accepted
**Date:** 2026-07-06
**Context:** директива владельца 2026-07-05/06 («знать ВСЁ про аудиторию своими
силами, как Метрика; BI уровня executive; LLM-Пульс видит всю аналитику дня»).
План «Аналитика 2.0: сбор, цели, BI». Строится поверх ADR-0009 (сырой
поведенческий поток) — этот ADR добавляет слои идентичности, вычислений и
представления.

## Решение: пять слоёв поверх сырья

```
сбор (behavior.js/track.js, ADR-0009 + расширения)
  → идентичность (visitor_id, identity_links, мост _ym_uid)
    → вычисления (server_sessions, goal_taxonomy, rollup'ы)
      → витрины (analytics_marts — одна точка истины)
        → потребители (BI 10 разделов, Пульс-LLM, телеграм-бот, алерты)
+ OLAP-копия (ClickHouse) для произвольных срезов
```

### 1. Идентичность

- **`visitor_id`** — UUID в localStorage (`fe:analytics:visitor`), живёт годами —
  аналог clientID Метрики. Хэшируется на бэке (`stable_hash` → `visitor_id_hash`)
  и пишется в `frontend_events`, `behavior_events`, `behavior_sessions`.
- **Ретро-мост в Метрику**: `session_start` читает first-party cookie `_ym_uid`;
  значение хэшируется ТЕМ ЖЕ `stable_hash`, что `raw_metrika_visits.client_id_hash`
  — join даёт новому visitor_id историю визитов Метрики (retention не с нуля).
- **Граф идентичности**: таблица `identity_links` (user_id × visitor_id_hash,
  first/last_seen). При логине visitor привязывается к user — гостевая история
  ретроспективно принадлежит человеку; кросс-девайс — только через аккаунт,
  вероятностный fingerprint-матчинг НЕ делаем.
- **Гео своими силами**: DB-IP Lite City mmdb (`services/geoip.py`,
  автоскачивание + ежемесячное обновление), lookup по client IP из
  X-Forwarded-For → country/region/city в `behavior_sessions`. Сам IP не
  храним (152-ФЗ).
- **Канал**: серверная классификация (`services/traffic_channel.py`) по
  referrer/UTM/yclid — модель last non-direct click, как у Метрики.

### 2. Вычислительный фундамент (`tasks/analytics_rollups.py`)

- **Серверная сессионизация**: логическая сессия = visitor_id + разрыв ≥30 мин
  (правило Метрики) → таблица `server_sessions`. Клиентский session_id остаётся
  технической единицей батчей. ВСЕ витрины уровня «сессия» (воронка,
  вовлечение, конверсия) считаются ТОЛЬКО на серверных сессиях.
- **Таксономия целей** (`services/goal_taxonomy.py`): каждое бизнес-событие →
  tier `macro` / `micro` / `engagement` / `technical` + вес скоринга.
  Ошибки и показы баннеров — technical, в воронку НЕ входят. Словарь целей
  Метрики (`metrika_goals`) синкается ежедневно из Management API — числа
  `goals_json` расшифровываются, конверсия Метрики считается только по
  бизнес-целям.
- **Rollup'ы**: `daily_traffic` (день × канал × устройство × новизна),
  `daily_goals` (день × событие × tier), `daily_pages` (день × страница).
  Инкремент последних 2 суток каждые 15 минут, хвост 60 дней — ночью.
  Все пересчёты идемпотентны (delete окна + bulk insert).

### 3. Единый слой витрин (`services/analytics_marts.py`)

Каждая витрина — одна функция; потребители (BI-дашборд `admin_bi.py`,
Пульс-снапшот `pulse.py::snap["marts"]`, телеграм-бот, алерты) читают ОДНИ
функции — цифра в дайджесте и на экране BI по построению одна и та же.
Дублирование агрегаторов pulse/admin_bi устранено импортом общих примитивов.

### 4. BI: executive-модель (10 разделов)

`/admin/bi`: Дерево (North Star визиты/день + 4 драйвера с таргетами из
`data/bi_targets.py` и статус-цветами) · Привлечение (+сегменты, +деньги
Директа) · Аудитория (портреты, гео, «Люди» со скорингом) · Поведение (sankey,
sunburst, блочное внимание) · Конверсия (собственная realtime-воронка +
истинная воронка Метрики) · Удержание · Спрос и SEO · Что менять (квадранты
разделов, adoption, copy) · Срезы (OLAP) · Надёжность (vitals p75, JS-ошибки,
латентность API, полнота сбора). Badge источника («Метрика»/«наш счётчик») на
карточках. ECharts (tree-shaken, `components/EChart.jsx`) — для sankey /
sunburst / calendar-heatmap; Recharts остаётся для линий и баров.

### 5. OLAP-слой ClickHouse (`services/clickhouse_sync.py`)

- **Роль: производная копия.** Postgres — единственный источник истины; CH
  можно снести и налить заново (`resync`). Ни одного нового пути записи.
- Синк каждые 15 минут: append-only таблицы — батч по id-курсору (курсоры в
  state-Redis DB 1), сессии/визиты — перезаливка последних 2 суток
  (ReplacingMergeTree дедуплицирует). Идемпотентный DDL на старте.
- Вкладка «Срезы»: метрика × ≤2 измерения × период через белый список
  (`SLICE_METRICS`/`SLICE_DIMENSIONS`) — произвольный SQL исключён; admin-only.
- **Деградация**: CH упал → сайт/сбор не замечают, «Срезы» отвечают 503 с
  человеческим текстом, синк догоняет. Том `clickhouse_data` в бэкапы не
  входит — восстанавливается ресинком.

### Realtime-аномалии (`services/analytics_alerts.py`)

15-минутный цикл: обвал трафика часа (<40% того же часа прошлой недели),
всплеск js_error, тишина собственного сбора, лаг Метрики >36 ч, лаг CH-синка.
Антиспам — 1 алерт на тип в 2 часа (Redis). Канал — Telegram владельцу.

## Инварианты

1. **Session-слой — только серверный.** Воронка/вовлечение/конверсия не
   считаются на клиентских session_id — иначе сверка с визитами Метрики
   некорректна по определению.
2. **Одна точка истины на цифру.** Новая аналитическая цифра появляется как
   функция в `analytics_marts`, потребители импортируют — не пересчитывают.
3. **Ошибки — не цели.** Technical-tier не участвует в воронках и скоринге;
   его место — раздел «Надёжность».
4. **CH — вторичен.** Любой код обязан переживать недоступность ClickHouse;
   деплой и бэкапы его не учитывают.
5. **Приватность**: IP не хранится (только гео-производная), идентичность —
   first-party, вероятностного матчинга нет.

## Последствия

- Метрика остаётся референсом для сверки (норма расхождения сессий/визитов
  <15%), но не единственным источником: собственный слой — realtime и полный.
- Пульс-LLM получает полный дневной контекст (`build_marts_daily_context`).
- CPA/ROI Директа — каркас `direct_costs` готов, коннектор включается после
  передачи API-токена владельцем.

## Subsequent additions (after acceptance)

**2026-07-06 — операционная доводка при локальном smoke:**

- **ClickHouse low-memory профиль обязателен.** Образ CH под cgroup-лимитом
  ~1 ГБ на baseline съедает почти весь лимит, и любой `GROUP BY` в «Срезах»
  падает с `MEMORY_LIMIT_EXCEEDED` (code 241). Профиль вынесен в
  `clickhouse/low-memory.xml` (config.d: урезаны кэши, `max_server_memory_usage_to_ram_ratio`,
  отключены `*_log`-таблицы) и `clickhouse/low-memory-users.xml` (users.d:
  `max_memory_usage=300 МБ` на запрос, external group by/sort на диск как
  страховка). **`background_pool_size` НЕ трогать** — merge_tree sanity-check
  требует согласованности с `number_of_free_entries_in_pool_to_execute_mutation`,
  иначе CH не стартует (code 36). Убрана `CLICKHOUSE_SKIP_USER_SETUP=1` — с ней
  пароль `default` не применялся (AUTHENTICATION_FAILED).
- **GeoIP-том должен принадлежать appuser.** `/app/geoip` — mountpoint именованного
  тома `geoip_data`; без предварительного `mkdir + chown` в Dockerfile docker
  инициализирует его от root, и автоскачивание mmdb падает с Permission denied.
  Строка `mkdir -p /app/geoip && chown` добавлена до `USER appuser`.
- **`resync()` льёт всю историю, не 2-дневное окно.** Полный ресинк — это
  бутстрап пустого CH: replacing-слои (сессии/визиты/identity) заливаются с
  `days=3650`, иначе после ресинка в CH нет исторических визитов Метрики. Все
  CH-вызовы вынесены в executor (клиент синхронный), курсор последнего синка
  выставляется — иначе первый инкремент после ресинка думает, что синк не шёл.

**2026-07-06 — BI 2.1 (план «период МСК, наш счётчик как истина, визуальная чистка»):**

- **Редизайн целей.** Все ~92 бизнес-события фронта явно классифицированы в
  `goal_taxonomy.py` (macro/micro/**intent**/engagement/technical) с тестом
  полноты против реестра `track.js`; словарь Метрики получил soft-delete
  (`MetrikaGoal.deleted` — цель удалена из счётчика, историческая резолюция
  имён живёт); в кабинете Метрики выполнена чистка до ~24 целей + 2 воронки
  (скрипт `backend/scripts/metrika-goals-redesign.py`); синк-гвард не даёт
  расхождению кабинета и словаря пройти незамеченным. Скоринг «Людей» получил
  кэп повторяющихся событий.
- **Period-движок (`analytics_period.py`).** `Period` (МСК-день 00:00 →
  текущий момент, пресеты today/yesterday/7d/30d/90d + custom from/to) —
  единственный способ задать окно: все витрины `analytics_marts`, `admin_bi`
  и API `/admin/bi/dashboard` принимают `Period`, meta периода уходит на фронт
  и подписывается на карточках. Легаси `?days=N` продолжает работать через
  `as_period`.
- **Антибот и самоисключение.** `bot_score.py` — эвристический скоринг 0–100
  на сессионизации (`ServerSession.bot_score`, `is_bot = score >= порога`);
  `isTrusted` кликов собирается в `behavior.js`. Собственная активность
  (админ-идентичности, страницы `/admin/*`, свой домен в referrer) помечается
  `ServerSession.is_internal` и исключается из витрин отдельно от ботов.
  Приёмка: небот-сессии в коридоре ±15% к визитам Метрики (витрина
  «Роботность» показывает коридор и вклад эвристик).
- **Наш счётчик — истина.** North Star, календарь года, KPI, трафик по дням,
  пульс недели, donut источников, конверсии и поисковики считаются от
  собственных небот-сессий; Метрика — референс через per-карточный
  переключатель «сравнить с Метрикой» (`useMetrikaCompare`, localStorage).
  Конверсия в «Сегментах»/«Качестве каналов»/«Посадочных» — только по
  business-tier целям. Блоки, живущие только на данных Метрики, помечены
  бейджем слоя.
- **Визуальный слой.** Единый словарь ярлыков `frontend/src/lib/biLabels.js`
  (каналы, устройства, поисковики, языки, таймзоны, города, блоки, срезы) +
  тултипы методики (`MethodHint`) у драйверов и сложных карточек; фразы —
  таблицей со схлопыванием недопечаток; пороги малых выборок; ошибки JS
  свои/сторонние; API-латентность таблицей p50/p75/max; РСЯ и sticky-шапка
  убраны с `/admin/*`. Alembic `20260706_bi21` (deleted/bot_score/is_internal).

**2026-09-03 — изоляция аналитического пула.** Инцидент: rollups/Pulse/CH-синк
держали `idle in transaction` на том же engine, что витрина. Канон:
`analytics_engine` (pool 2+2, statement 60 с, idle-in-tx 120 с);
публичный engine — timeout 30 с / pool_timeout 10 с. Короткие сессии
по фазам. `/metrics`: pool/RSS/cgroup. Алерты memory_pressure /
db_pool_saturation / idle_in_tx. ClickHouse лимит 448M; backend на 4 ГБ
хосте 1 ГиБ (1536M — после апгрейда RAM).
