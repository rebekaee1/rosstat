# Сопровождение знаний при обычной задаче

**Действует с:** 2026-09-30. Владелец задаёт желаемый результат обычным промптом.
Агент выполняет этот цикл сам; специальная команда на документацию не требуется.
Полнота первоначального досье принимается по [K01–K12](code-review/readiness-criteria.md).
Поддержание текущести и содержательное понимание проверяются отдельно.

## 1. До изменения

Зафиксируй HEAD/ветку/рабочий diff. Прочти основной документ темы и затронутый
код, рецензии, ADR и исторические основания. Проследи consumers/producers,
контракты и конфигурацию. Для каждого затрагиваемого механизма установи вход,
результат, побочные эффекты, error/empty/partial/retry и границы процесса.

Закончить чтение можно, когда перечислены все затронутые механизмы и документы,
известные противоречия объяснены либо зарегистрированы. Вопросы об устройстве
агент выясняет по проекту; владельцу задаётся существенная неоднозначность
желаемого продукта, которую источники не разрешают.

## 2. Основной источник каждой темы

| Изменение | Содержательное обновление |
|---|---|
| Возможность продукта, новая подсистема | README: краткий обзор; CONTEXT: сущности/границы/инварианты; architecture: связи и сценарии; contracts: формат, состояния, права и lifecycle |
| Source/парсер/endpoint/model_config | `data_sources.md` и docstring парсера; реестр, seeds, источник/пол истории и контракт публикации |
| Derived/forecast/view-mode/variant/категория | Рецепты в `agent-recipes.md`, playbook, реестры и generated-зеркала; формула/частота/единица/пустота; листинг, поиск, homepage и RU/EN |
| API, UI, сообщения, экспорт | Публичный контракт и потребители; роуты/OpenAPI; семантика отображения, доступ, состояния, SSR/SPA и языки |
| Identity/аналитика/BI/бот/MCP/внешний клиент | ADR и `analytics_api_inventory/`; права/retention/атрибуция/ошибки/поток наружу; фактические ограничения доступа |
| Конфигурация/dev/CI/deploy/cache/ресурсы | `workflow.md`, `enterprise_resilience.md`, architecture; defaults/precedence/restart/build. Runtime — новое датированное наблюдение разрешённых полей без секретов |
| Новое архитектурное решение | Новый ADR при смене инварианта/оси декомпозиции; при эволюции — dated Subsequent additions существующего ADR. Ссылка в CONTEXT и history |
| Исправление знания или исторического статуса | Прочитать старое основание, добавить текущий статус и заменивший механизм; первоначальные причины и исходные артефакты сохранить |
| План, завершение, неизвестное | Один backlog: статус, затронутые места, доказательства, остаток. Специализированные свидетельства — `docs/code-review/`, основная инструкция остаётся в тематическом документе |

У каждой темы один основной источник. Копии дают ссылку; generated-артефакт
обновляется через свой исходник. DOCX/PDF/XLSX/схема/запись, если они содержат
требование или объяснение, входят в [реестр материалов](code-review/readiness-criteria.md#все-форматы-и-места-хранения-знаний).
Название или метаданные картинки не закрывают разбор её содержимого.

## 3. После реализации

1. Проверь затронутые сценарии подходящими тестами и, для UI, браузером.
   Запиши, что проверено локально, что подменено, что требует production acceptance.
2. Обнови основные документы и исторические статусы по таблице. Новая функция
   должна быть привязана к сущностям, входам, API/jobs, хранению и окружению.
3. После чтения обнови соответствующие строки `docs/code-review/reviews.jsonl`:
   SHA, назначение, контракты, ошибки/эффекты, элементы и основания проверки.
   Допустимо прежнее полное чтение + содержательная дельта; явно запиши старый
   hash/commit, прочитанные changed ranges и проверенные зависимости. Сам по себе
   неизменённый AST не устанавливает неизменность поведения вызываемого сервиса.
4. Добавь в index только принадлежащие задаче файлы и проверь staged diff.
   Публикуемые карты строятся по Git tracked/index inputs выбранной `main`,
   включая staged новые файлы. Чужие untracked материалы сохраняются отдельно
   и не становятся частью снимка main или коммита автоматически.
5. Пересобери символы и карты командами ниже. Просмотри изменения рельефа и
   убедись, что новые механизмы, маршруты и внешние границы учтены.
6. Актуализируй [реестр материалов](code-review/materials-current.json): новые
   пути, версии/SHA, назначение, основной источник и честный статус чтения.
   Сам реестр и его pointer исключены из собственного хеша. Остальные tracked
   материалы `docs/`, включая ручные критерии и свидетельства `code-review/`,
   проверяются отдельным `audit-knowledge-materials.py --check`. Generated
   значения обновляются после генерации; hash не присваивает статус чтения.

```bash
node scripts/code-review-symbols.mjs --tracked-only
python3 scripts/audit-code-documentation.py --build --tracked-only
# Локальный изолированный Python с graphifyy==0.9.69:
/Users/iprofi/.codex/tools/graphify-venv/bin/python scripts/build-project-terrain.py --refresh --tracked-only
# Если среда Graphify находится в другом месте, используй её Python.
./scripts/check-project-knowledge.sh
./scripts/check-all.sh
```

`--build` не пишет рецензии и не скрывает пробелы. `--refresh` извлекает структуру,
не принимает семантические решения. `--check` работает без Graphify и доступа
к серверу; для сохранённого снимка использует тот же input scope. В обычном
check/CI артефакты проверяются без перезаписи. HTML не хранится в Git:
`python3 scripts/build-project-terrain.py --render` восстанавливает просмотрщик.

## 4. Условие завершения и передача

Каждое затронутое место имеет актуальный код, тематический документ, рецензию,
карту и проверку либо явное ограничение. AGENTS ведёт к теме, ссылки разрешаются.
Источник ошибки/решения, реализованное поведение и свидетельство окружения
различимы. Факт наличия кода не означает выпуск на сервер.

Knowledge job в CI и локальный knowledge-check выявляют stale SHA, отсутствующие
файлы/аннотации, дрейф карты, материалов и размер входа AGENTS. Они не оценивают истинность
прозы. При новой подсистеме расширь K02–K09 и сквозные сценарии.

После крупных изменений проведи испытание агента без истории чата: дать только
репозиторий, AGENTS и обычную задачу; проверить поиск оснований, устройство
сценария, влияние изменения, различие main/dev/prod, сохранение старых решений
и честное перечисление неизвестного. Сохранить отчёт с источниками и исправить
обнаруженные пробелы. Успешная проверка ограничена её сценариями.

В итоговом сообщении коротко перечисли выполненное, проверки, commit и оставшиеся
ограничения. Следующий чат получает основания из репозитория, а не из обещания
помнить всю предыдущую переписку.
