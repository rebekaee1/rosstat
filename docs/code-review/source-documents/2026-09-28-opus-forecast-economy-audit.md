- **Трафик** [D]:

  - Людей около 350 в день, 659 просмотров в день.

### Как деплоится [F/D]

1. Деплой запускается вручную от root командой `ssh fe-prod 'bash /opt/rosstat/scripts/deploy.sh'`.
2. Скрипт делает бэкап и проверяет коммит по списку `deploy/approved-shas.txt`.
3. Затем выполняет **`docker compose build` прямо на боевом сервере**. Старые контейнеры в это время продолжают обслуживать сайт.
4. Дальше выкладываются ассеты, контейнеры перезапускаются, сбрасывается SSR-кэш. Потом идут проверки и 15 минут наблюдения.
5. Весь деплой занимает 20–25 минут.

Проблемы этой схемы:
- **Сайт недоступен (502),** пока новый backend выполняет миграции и три сид-скрипта. После каждого деплоя кэш пустой.
- **CI проверяет не то, что уходит на прод.** CI собирает свой образ и выбрасывает его, на прод уходит другая сборка. `deploy.sh` статус CI не проверяет.
- **Откат ограничен.** Если миграции изменились, откат отказывается работать. Базу он не откатывает никогда.
- **Три неудачных деплоя за четыре недели:**
  - 27.08: 502 около 40 минут, обрезаны 9643 точки данных (потом восстановлены);
  - 26.09: холодный кэш, ошибки 503, откат;
  - 27.09: откат оставил новую миграцию под старым кодом.

### Наблюдаемость [D]

- Логи Docker хранятся всего несколько часов. Центральных логов нет.
- Sentry на backend нет. На frontend он фактически выключен: DSN не попадает в сборку.
- Метрик (Prometheus или Grafana) нет. Внешняя проверка доступности не подтверждена.
- Проверки памяти и пулов соединений смотрят только на `scheduler`. После разделения процессов веб-часть никто не мониторит.
- Флаги защиты от скрейпинга включены, но функция `should_block()` возвращает `None`, то есть ничего не делает.

## 2. Почему сайт жил на одном ядре

Хронология [F]:

| Дата | Что было |
|---|---|
| 25.02 | Timeweb, **1 CPU / 2 ГБ** |
| 12.04 (`396df11`) | Откат на **1 воркер**. Планировщик APScheduler жил внутри веб-процесса, и с двумя воркерами «сбор данных шёл дважды» |
| 03.09 | Апгрейд до **8 ГБ / 4 vCPU** |
| 04.09 (`dc05b82`) | У backend по-прежнему лимит `cpus: '1.0'`. Переменная `UVICORN_WORKERS` в compose **не передавалась в контейнер**: настройка в `.env` молча ничего не делала |
| 26.09 | Замер: ~15 запросов/с. Всплески ботов (800–1100 в минуту) пять раз за день положили сайт на 10–35 минут. Хост при этом **простаивал на 77%**, свободно 5,3 ГБ памяти |
| 26.09 (`dfecc66`) | Разделение процессов: 3 веб-воркера и отдельный `scheduler` |

Итог: 5,5 месяца на одном воркере, из них **23 дня** с доступными четырьмя ядрами.

Четыре причины, все архитектурные:
1. **Фоновые задачи жили в веб-процессе.** Масштабировать веб значило дублировать сбор данных.
2. **Лимит CPU в Docker.** `cpus` — это квота процессорного времени, а не число видимых ядер. Внутри контейнера `os.cpu_count()` врёт.
3. **Настройка молча терялась по дороге** из `.env` в контейнер. Ни один тест этого не ловил.
4. **Никто не видел загрузку каждого ядра.** Метод USE Грегга показал бы «одно ядро на 100%, три свободны» за минуты.

**Урок для v2:**
- Роли (витрина, сбор, сборка) — это отдельные процессы с первого дня.
- Число воркеров равно числу ядер, и тест в CI проверяет, что настройка реально доходит до процесса.
- Графики загрузки по каждому ядру с алертом.

По подсчёту аудита, одно и то же знание хранится в **27 местах, и автоматически связаны только 5** из них: два сгенерированных JSON и три regex-теста.

**Два независимых рендера каждой страницы.** Это около 22 тыс. строк Python и около 32 тыс. строк React. Теста, который сравнивает их результат, нет. React не гидрирует серверный HTML, а стирает его (`createRoot`) и строит страницу заново через API.

Расхождения, которые есть прямо сейчас [F]:
- **Заголовки.** У мировых показателей SSR и React выдают разный `<title>`, и `useMeta.js` перезаписывает серверный. Именно такое «мигание» заголовка код сам называет причиной выпадения страниц из Яндекса 29.04.
- **Формат чисел.** На `/russia/today/…` одни и те же значения выглядят по-разному:

  | Значение | SSR | React |
  |---|---|---|
  | 1234,56 | `1 234,56` | `1 235` |
  | 123,45 | `123,45` | `123,5` |
  | −0,5 | `−0,5` | `-0,5` |

- **Годовые страницы.** URL `/russia/indicator/{code}/{year}`: сервер отдаёт отдельную годовую страницу, а React ведёт на живую карточку.

**API без типов** [F]:
- Схема ответа объявлена только у 10 из 81 JSON-маршрута.
- Генерации TypeScript-типов из OpenAPI нет.
- Страница мирового показателя по очереди перебирает пять полей, чтобы найти единицу измерения.

**Кэш держится на ручной проводке** [F]:
- **Порядок.** Кэш сбрасывается **до** записи данных в базу: `base_parser.py`, строки ~209–222. Кто успеет прочитать в этот момент, закэширует старые данные под новой версией.
- **Пространства имён.** Это произвольные строки примерно в 55 местах. Ошибки сброса проглатываются. Если ключа версии нет, берётся «0».
- **Настройки прода.** Там стоит `allkeys-lru`, и Redis вытесняет сами ключи версий. После этого оживают старые записи.
- **Сбросы, которые ничего не делают.** Региональный API использует фиксированные ключи `fe:regions:…`, поэтому сброс «regions» после загрузки EMISS на них не действует. `ssr-region` не сбрасывается нигде.
- **Прогнозы.** Пересчёт прогнозов не сбрасывает кэш вообще. Ключ прогнозов 11 недель жил без версии.

**Нет правила «кто владеет данными»** [F/D]:
- **Сид против ручных правок.** Сид при каждом изменении каталога перетирает SEO-тексты, которые редактировали в базе. А ADR-0003 обещает, что эти тексты правятся без деплоя.
- **Сид против EMISS.** `seed_regional` делает TRUNCATE+COPY той же таблицы, в которую пишет EMISS.
- **Частичные ответы источников** удаляют уже сохранённую историю.
- **ClickHouse** забирает события по курсору `id`, поэтому часть строк может потеряться навсегда. Сверки нет.
- **EN-домен.** Если перевода нет, показывается русский текст. Так на английский домен утекла кириллица: 1531 из 1866 рядов BEA.

## 5. Корневые причины

1. **Нет единой модели «страницы».** Страница размазана по 8 местам и двум языкам. Новое семейство требует около 8 согласованных правок.
2. **Рендер по запросу на огромном пространстве URL.** Кэш не может помочь, когда боты равномерно обходят 20 млн адресов.
3. **Всё в одном приложении и на одном диске.** Сайт, сбор данных, прогнозы, картинки, аналитика, Telegram, LLM-отчёты — это 39 задач в `main.py`. Одна тяжёлая задача роняет всё:
   - 04.09: BI плюс боты на OG-картинках;
   - 26.09: холодные рендеры исчерпали пул соединений;
   - 27.09: ротация логов вызвала 48 таймаутов SQL.
4. **Согласованность данных поддерживается вручную:** кэш, владение таблицами, типы API.
5. **Эксплуатация без страховки.** Сборка на проде, внешнего бэкапа нет, метрик нет.
6. **Страницы генерируются от предложения, а не от спроса.**
   - Старейшее комбинаторное семейство — 0,9 млн страниц «регион × показатель × год». Оно дало 0 кликов в Google и 53 визита за сентябрь.
   - После 20.09 добавили ещё около 9 млн таких комбинаций. Данных о них пока нет, но картина та же.
7. **ИИ-агенты координируются прозой.**
   - Документы огромные: AGENTS.md 85 КБ, CONTEXT.md 168 КБ, backlog 342 КБ.
   - Документы расходятся с кодом: README до сих пор описывает разделение ботов по User-Agent, которое убрали в апреле, и несуществующий «sshscript».
   - `seo_renderer.py` одновременно «застолбили» шесть зон.
   - Семь PR закрыты без слияния, в worktree остались неслитые ветки.

## 6. Генератор v2

### Главная идея

**Данные → проверенные факты → реестр страниц → один рендер в файлы → раздача файлов.** Страница существует, только если у неё есть спрос, и описана она ровно в одном месте.

Бытовая аналогия: сейчас сайт работает как типография, которая печатает газету заново для каждого читателя. v2 печатает тираж один раз, когда меняются новости, и раздаёт готовые экземпляры.

```
источники ──► сырые снимки ──► факты (схема) ──► производные (граф) ──┐
                                                                      ▼
Wordstat/GSC ──► реестр страниц (порог спроса и качества) ──► сборщик ──► файлы HTML/OG
                                                                      │  атомарная публикация
                                                                      ▼
                                          nginx + российский CDN ──► люди и боты (один и тот же HTML)
                                                                      │
                          воронка по семействам: опубликовано → в индексе → клики ──► реестр
```

### Модули

Каждый модуль глубокий: маленький интерфейс, один владелец, контракт.

1. **Адаптер источника.**
   - Работает так: `fetch → сырой снимок` (неизменяемый файл с датой), потом `parse → строки` по схеме.
   - Адаптер обязан объявить, полный ответ пришёл или частичный. Частичный ответ никогда не удаляет историю.
2. **Хранилище фактов.**
   - Postgres, типизированные таблицы: сущность, метрика, период, значение, единица, источник, ревизия.
   - **У каждой таблицы один писатель.**
   - Каталог и тексты хранятся как данные (YAML/CSV со схемой). Они загружаются явной командой, а не при каждом старте контейнера.
3. **Производные.** Чистые функции с объявленным графом зависимостей. Этот же граф решает, какие страницы пересобрать. Ручных «namespace» больше нет.
4. **Реестр страниц** — сердце системы. Семейство описывается один раз:
   - шаблон URL;
   - какие факты нужны;
   - ключ спроса (шаблон фразы Wordstat);
   - порог качества: минимум данных, уникальность, спрос;
   - шаблон страницы, локали, правила canonical/hreflang, OG, перелинковка.

   Из реестра **генерируются** маршруты, карта сайта, список для IndexNow, hreflang, хлебные крошки, ссылки и тесты.
5. **Сборщик.**
   - Jinja2 рендерит страницы в файлы: `.html` плюс `.br`/`.gz`, и OG-картинки.
   - Хэш страницы считается от версии шаблона и куска данных. Пересобираются только изменённые страницы.
   - Пул процессов: воркеров столько же, сколько ядер.
   - Публикация атомарная: сборка в новую папку и переключение ссылки.
   - Оценка [I]: Jinja выдаёт сотни–тысячи страниц в секунду на ядро. Значит, 30 тыс. страниц на 4 ядрах соберутся за минуты.
6. **Раздача.**
   - nginx отдаёт файлы, перед ним российский CDN. У Yandex Cloud CDN есть точки во Франкфурте и Амстердаме. Cloudflare для российских пользователей с июня 2025 фактически не работает [V].
   - **Боты и люди получают один и тот же HTML.**
   - Интерактив (калькулятор, график, PDF) сделан маленькими «островами». Они читают JSON, встроенный в ту же страницу, поэтому данные разойтись не могут.
7. **Маленький API** только для по-настоящему динамического: оплата, персональный расчёт, поиск. Это отдельный процесс, воркеров = ядер.
8. **Воронка SEO.**
   - Каждый день по каждому семейству: в карте сайта → обходится ботом (логи) → в индексе (API Вебмастера и GSC) → клики.
   - Если семейство ниже порога через N недель, его перестают публиковать (410 или склейка). Победители расширяются.

### Многоядерность «по умолчанию»

- Роли разнесены по процессам: витрина, сборщик, сбор данных, аналитика.
- Воркеры считаются по реальной квоте CPU. Задать `PYTHON_CPU_COUNT`, а не полагаться на `os.cpu_count()`.
- Нагрузочный тест (k6) до запуска, чтобы знать, сколько запросов в секунду тянет одно ядро.
- Fitness-тест в CI: «настроено N воркеров — запущено N процессов».
- Для этой нагрузки free-threaded Python 3.14 не нужен: он официально поддерживается, но опционален [V].

### Деплой и эксплуатация

- **Образ собирается в CI** (GitHub Actions) и публикуется в реестр. Сервер только скачивает его: Kamal от 37signals или `compose pull`. Замена без простоя, откат одной командой [V].
- **Миграции** — отдельный шаг по схеме expand/contract. Сиды не живут в entrypoint.
- **Бэкап:**
  - ночной дамп плюс WAL в Object Storage (pgBackRest или wal-g);
  - автоматическое пробное восстановление раз в месяц;
  - алерт, если копия старше 26 часов.
- **Мониторинг:**
  - node_exporter, cAdvisor и Prometheus с Grafana (или один Netdata);
  - внешняя проверка доступности;
  - Sentry;
  - алерты: перекос по ядрам, диск больше 75%, память, 5xx, возраст бэкапа.
- **Диск.** Бэкапы и логи хранятся не на диске базы.

### Работа с ИИ-агентами

- **Правила архитектуры — автотесты** (fitness functions):
  - правила импортов;
  - проверка дрейфа сгенерированных файлов;
  - бюджеты скорости;
  - проверка ссылок.
- AGENTS.md короткий, до 5 КБ. Все счётчики генерируются из кода.
- **Концептуальная целостность держится на одном архитекторе.** Это ты: агенты исполняют, реестр и контракты утверждаешь ты.
- Короткие PR прямо в main, без долгоживущих worktree.
- **Агентам запрещено удалять тесты.**

### Фабрика ниш

Ядро общее: адаптеры, факты, реестр, сборщик, воронка, деплой. Ниша — это **пакет**: источники, схема фактов, семейства страниц, шаблоны, тексты.

Детский сайт станет первым пакетом, собаки или клиентский сайт — вторым. Семейства Росстата, которые реально приносят трафик, потом переносятся отдельным пакетом.

### Что значит «в 5 раз лучше»: измеримые цели

| Метрика | Сейчас (FE) | Цель v2 |
|---|---|---|
| Сколько правок нужно на новое семейство страниц | ~8 мест, 2 языка | 1 запись в реестре + 1 шаблон |
| Копии одного знания без автоматической проверки | 22 | 0 |
| Стоимость ответа на запрос | рендер на Python, ~15 запросов/с на воркер | готовый файл из nginx/CDN, в сотни раз дешевле |
| Деплой | 20–25 мин, окна 502, холодный кэш | 1–3 мин, без простоя, откат одной командой |
| Доля опубликованного в индексе | < 0,3% | ≥ 50% |
| Восстановление | ни разу не проверялось | проверяется ежемесячно, RPO ≤ 1 сутки |
| Загрузка ядер | не видна | видна по каждому ядру, с алертами |

### Чего НЕ делать

- **Эффект второй системы (Брукс).** Вторую систему тянет вместить всё, чего не хватило в первой. Не переносить в v2 BI, ClickHouse, OAuth, «Пульс» и Telegram, пока без них можно обойтись.
- **Правило D-I-D (Эбботт и Фишер):** проектировать на 20×, строить на 3×, разворачивать на 1,5×.
- **Не генерировать миллионы комбинаций.** Политика Google о дорвеях прямо называет страницы «под регионы и города», ведущие на одну страницу. Яндекс исключает маловостребованные страницы и пересматривает решение почти ежедневно [V].
