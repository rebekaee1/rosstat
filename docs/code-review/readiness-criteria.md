# Когда рельеф проекта готов к содержательному анализу

**Назначение:** критерии завершения сбора знаний о Forecast Economy перед обсуждением оптимизации, исправлений и новой архитектуры.

**Основание:** запрос владельца 27 сентября 2026 — сначала собрать устройство проекта и иметь все доступные материалы, затем анализировать. Критерии выведены из текущих исходников, документации, истории решений, реестра рецензий и датированного снимка окружений. При подготовке HEAD локальной `main` — `5534d0f2a6d836613bf03890440dd60eef1fc522`; в рабочем дереве параллельно менялся код других задач. Этот документ задаёт условия приёмки; он не объявляет их выполненными.

## 1. Что должно получиться

Связанное досье, по которому можно объяснить каждую обнаруженную часть системы: зачем она существует, как устроена, что получает, что изменяет, от чего зависит и как её поведение определяется данными и окружением. Для утверждений доступны основания; для неизвестного — результаты поиска и способ получения ответа.

Материалы остаются в репозитории, чтобы следующий агент или разработчик мог восстановить понимание без истории чата. Обзор ведёт к подробностям; подробности возвращают к сценарию и назначению системы.

Готовность досье не означает отсутствие дефектов. Требуемое поведение, реализованное поведение и фактически наблюдавшееся поведение описываются отдельно. Если код нарушает требование, оба состояния и их расхождение сохраняются в досье.

## 2. Полнота считается по нескольким независимым спискам

Список рецензий нельзя использовать как единственный источник списка объектов: иначе пропущенный при описании объект исчезает и из знаменателя. Для каждого вида нужен независимый инвентарь из регистраций, деклараций, файлов или наблюдений окружения.

| Вид объектов | Откуда брать полный список для выбранного среза | Что связывать с описанием |
|---|---|---|
| Исходники, документы, ресурсы | Git tracked + неигнорируемые рабочие файлы; отдельный список существенных ignored/generated материалов | Статус, источник, версия, назначение; причина каждого исключения |
| Функции, классы и исполняемые блоки | AST Python/JS плюс прямое чтение SQL, shell, HTML/CSS/Mako, модульных блоков и callbacks | Механизм, входы/выходы, условия, эффекты, ошибки; анонимные блоки имеют собственный anchor или явно указанный содержащий блок |
| Декларации и динамические реестры | Parser registry, DERIVED_SPECS, FamilyDef, forecast registry, variants, frequency links, provider/reference-конфиги | Каждая запись → параметры → resolver/генератор → фактический обработчик → потребитель |
| Пользовательские поверхности | SPA routes, вложенные/embedded routes, страницы и управляющие компоненты | Экран/действие → состояние → hook/query → API; loading/empty/error/stale/access states; RU/EN и существенные варианты отображения |
| HTTP и публичные URL | FastAPI mounts/routers, SSR/sitemap/OG/RSS/export, nginx/Caddy rules, redirect/canonical registries | Host + метод + path → middleware/access → handler → ответ/redirect; различие SPA и SSR |
| Фоновые и ручные входы | Scheduler registrations, startup/shutdown tasks, host cron/systemd, CLI, CI, MCP tools, bot handlers | Trigger, флаги, расписание/timezone, процесс, повтор/перекрытие, эффекты, результат |
| Хранилища и сообщения | ORM + migrations + SQL/ClickHouse schema, Redis key builders, cookies/localStorage, volumes/files, event/payload schemas | Идентичность, значения, производители, читатели, срок жизни, изменение/удаление, восстановление |
| Настройки и зависимости | Settings, Compose mapping, Vite/build env, host configs, manifests/lockfiles, Dockerfiles | Default → переопределения → эффективное значение/версия → читатель → поведение; условия restart/rebuild |
| Эксплуатация и окружения | Compose, entrypoints, deploy/backup scripts, CI, датированные read-only наблюдения хоста/контейнеров | Процессы, ресурсы, сеть, данные, запуск, обновление, откат, обслуживание |
| Наблюдаемость | Metrics, журналы, health/readiness, heartbeat, состояния запусков, alerts и их потребители | Производитель сигнала → точный смысл → хранение/окно/сброс → порог → получатель/действие; отсутствие сигнала, подавление, ошибки доставки |
| Требования, решения и доказательства | CONTEXT, ADR, backlog, старые/удалённые документы, Git history, доступные записи решений, тесты и отчёты | Требование/решение → реализация → проверка → дата/статус; отменённые решения и открытые вопросы |

Списки описывают конечные объекты и семейства условий на выбранной версии. Все возможные сочетания пользовательских действий и значений не образуют конечный проверяемый список.

Однотипные записи можно описывать через общий механизм, если **каждая** запись привязана к нему, её собственные параметры сохранены, а исключения перечислены. Нельзя объявить все страны, индикаторы или режимы покрытыми по одному примеру. Для данных отдельно различаются схема/методология и проверка каждого наблюдения; для изображений — метаданные и просмотр содержания.

Если изображение, макет или запись содержит требование, решение либо свидетельство поведения интерфейса, требуется изучить само содержание. Метаданные такого материала не закрывают его смысловой разбор. Недоступный материал включается в реестр неизвестного.

### Минимальная карточка механизма

- Устойчивый ID, тип, имя, родительская подсистема, источник `path:line`, SHA или дата наблюдения.
- Назначение и связанный продуктовый сценарий/инвариант.
- Входы, выходы, единицы/форматы/состояния; предусловия и конфигурационные переключатели.
- Вызывающие и вызываемые стороны; чтение/запись; существенный порядок действий.
- Побочные эффекты; транзакция/lock/cache; error/empty/partial/retry/idempotency semantics.
- Требование, фактическая реализация, известные расхождения, тесты/наблюдения и их ограничения.
- История решения, если восстановлена; неизвестные с ID.

Поле `не применимо` требует основания. Описание «обрабатывает данные» или пересказ имени функции не закрывает карточку. Простой wrapper может ссылаться на подробный контракт делегата и описывать собственное отличие.

### Минимальная карточка связи

`from → relation → to`, слой/процесс/среда, условие активации, переносимые данные, порядок/синхронность, доказательство и его версия. Для внешней границы достаточен проверенный используемый контракт. Неразрешённый endpoint остаётся вопросом; его нельзя превращать в выдуманный узел.

## 4. Как выяснять неизвестное

Исследование ведёт агент. Обычные вопросы об устройстве кода, настройках и доступной истории не перекладываются на владельца.

1. Сформулировать точный вопрос и указать механизм/связь, которую он мешает объяснить.
2. Прочитать определение, callers/consumers, реестры, настройки, тесты и соседние контракты.
3. Сверить актуальные и старые документы, ADR, `git log/show/blame`, доступные указатели записей решений. Последний timestamp сам по себе не определяет истинность требования.
4. Если ответ зависит от среды — получить адресное read-only свидетельство с версией и временем. Наличие файла `.env.example` не устанавливает effective config.
5. Если ответ зависит от внешнего API/библиотеки — проверить используемую версию и первичный контракт. Полный аудит исходников всех транзитивных пакетов не является условием описания границы; локально изменённая зависимость входит в состав проекта.
6. Если чтения недостаточно для определения механики, использовать минимальную изолированную проверку. Измерение мощности, полномасштабные нагрузочные испытания и учения по отказам относятся к последующему этапу проверки свойств системы.
7. Если ответ не найден — записать проверенные источники, недостающее свидетельство и конкретный следующий способ его получить. Гипотезу не превращать в объяснение факта.

| Класс неизвестного | Пример | Влияние на завершение сбора |
|---|---|---|
| Незавершённое чтение | Не найден читатель поля; не проверен registry resolver | Блокирует готовность затронутого механизма; продолжить исследование |
| Противоречие текущего устройства | Документ и конфигурация называют разные state Redis | Установить версии/условия и разрешить расхождение; до этого соответствующий критерий не закрыт |
| Недоступное наблюдение | Не получен effective config host-сервиса | Область помечена неполной; список попыток и способ доступа обязательны. Не переименовывать в «не применимо» |
| Неизвестная история | Мотив решения не сохранился ни в документах, ни в Git | Допустимо явно обозначить; текущий механизм всё равно должен быть понятен. Владельца спрашивать, если мотив влияет на обязательное ограничение |
| Неизмеренное свойство | Предельный throughput, p99 под смешанной нагрузкой, RTO после аварии | Не блокирует описание конструкции; ограничивает соответствующие выводы. Фиксируется отдельная будущая проверка |
| Не принятое продуктовое решение | Какой RPO бизнес считает допустимым | Это решение владельца, а не факт, который можно вывести из кода. Описать имеющийся механизм и оставить целевое требование открытым |

Карточка неизвестного: `ID, вопрос, объект, влияние, класс, проверенные источники, недостающее свидетельство, следующий шаг, статус`. Она не считается закрытой после одной неудачной строки поиска.

## 5. Проверка понимания до анализа улучшений

Для каждого семейства механизмов провести проход по досье с проверкой по источникам. Независимый проверяющий выбирает элементы из инвентаря, а не из заранее удобных примеров. Выборочная проверка оценивает качество описаний; полноту состава отдельно подтверждают сверки K02.

Контрольные вопросы применительно к этому проекту:

1. По произвольному индикатору восстановить source → parser/config → факт → derived/forecast → API/SSR/SPA → единицу, подписи, режимы и доступность карточки. Объяснить существенные исключения.
2. По конкретному URL определить host/locale, nginx/Caddy путь, handler, проверки доступа, canonical/redirect и условия существования страницы. Различить поведение браузера, SSR и API.
3. По произвольному полю ответа указать первичный источник, формулу, момент обновления, null/stale semantics и потребителей. Объяснить, почему «данных нет» не равняется нулю.
4. По выбранному job указать trigger, timezone, флаги, процесс, lock, commit, retry и публикационные эффекты; что код делает при частичном результате и повторе.
5. По cache key объяснить namespace/generation/TTL, кто создаёт и меняет его, какие читатели используют и что происходит при отсутствии Redis по коду.
6. По UI-действию показать state/query/API цепочку и отображаемые loading/empty/error/access состояния; где участвуют единицы, частота и локаль.
7. По auth/analytics/MCP операции проследить identity, credential/session/access checks, данные на внешней границе и место сохранения результата.
8. По настройке назвать default, все переопределения, effective value по доступным средам, читателей и необходимость restart/rebuild.
9. Объяснить, что именно запускается на сервере с 4 vCPU, что разделяет ресурсы, где сохраняются данные и какие свойства мощности пока не измерены.
10. Описать чистый dev startup, обновление, откат и восстановление по текущим процедурам; отдельно указать, какие из них действительно испытывались и на какой версии.
11. Для старого решения показать исходное основание, последующие изменения и действующий механизм; не выдавать исторический план за текущую реализацию.
12. Для выбранного изменения перечислить затрагиваемые связи, материалы и существующие проверки. Это объяснение зависимости; предложение самого изменения относится к следующему этапу.
13. По показанию health/heartbeat/метрики или сообщению alert объяснить, что именно было проверено, за какое окно, что сигнал не проверяет и что означает его отсутствие.

Если ответ основан на догадке, соответствующая карточка возвращается в незакрытые. Для ожидаемого поведения без исполнения допустима формулировка «следует из исходника при таких условиях»; она не заменяет результат эксперимента.

## 6. Условия окончания этапа

Сбор объявляется завершённым для **указанного среза и границ**, когда одновременно:

1. Все независимые инвентари сопоставлены с досье. Нет неразобранных объектов и необъяснённых существенных связей внутри доступной области.
2. K01–K12 имеют основания и статус по каждой затронутой подсистеме. Сводный зелёный статус не скрывает частично закрытые области.
3. Нет открытых противоречий, мешающих объяснить текущее устройство; исторические разногласия сохранены с датами и статусами.
4. Пройдена проверка понимания, ссылки позволяют повторить объяснение, изменения после среза видны.
5. Остаточные неизвестные разделены на недоступное знание, утраченную историю, неизмеренные свойства и непринятые решения. Недоступная существенная область делает итог «готово с ограничениями», а не «полностью готово».

Один процент для всего проекта не вычисляется. Отдельно показываются состав, содержательные карточки, связи, сценарии, настройки/окружения и основания. `0` ошибок нынешнего guard означает только отсутствие проверяемых им пропусков и дрейфа.

Новый вид механизма расширяет инвентари и критерии. Перечень из двенадцати пунктов — проверяемая основа для этого проекта, не гарантия, что будущие изменения не откроют новую область.

## 7. Что уже установлено о текущем досье

- Есть файловый реестр и отдельные аннотации именованных Python/JS-определений. [Guard](../../scripts/audit-code-documentation.py) проверяет SHA, диапазоны, имя/строку и наличие текста; смысловую достаточность описания он не устанавливает.
- [Файловая проекция](../project-terrain.md) на предыдущем срезе исключала 2418 связей с отсутствующим endpoint и 2210 внешних/неразрешённых связей; 17753 внутрифайловые связи оставались в полном локальном Graphify-графе. Требуется классификация исключений и явный доступ к нужным внутренним/динамическим связям, а не механическое включение всех рёбер.
- Есть основные сквозные контракты и описания окружений; отдельная доказанная полнота списков маршрутов, jobs, конфигурационных ветвей и сценариев пока не установлена.
- [Заключительный раздел архитектуры](../architecture.md#что-эта-карта-не-подтверждает) сохраняет старое утверждение об отсутствии серверных флагов/объёмов, противоречащее добавленному runtime-снимку в том же документе. Это конкретный незакрытый пункт K11.
- Во время подготовки критериев read-only `audit-code-documentation.py --check` обнаружил 13 файлов, требующих внимания после параллельных изменений рабочего дерева. Снимок `1287/1287` относится к прежней версии; он не переносится автоматически на новый код. Точный список меняется вместе с рабочим деревом.
- Браузерная визуальная приёмка текущей версии просмотрщика не выполнена: доступ к file URL был отклонён политикой инструмента; выполнены DOM-проверки. Успешные тесты и ограничения предыдущего прохода сохранены в [validation](validation.json).

Эти наблюдения определяют незавершённый сбор. Данный документ не изменяет приложение, не обновляет автоматически рецензии чужих правок и не закрывает перечисленные пробелы.

## 8. Порядок дальнейшего сбора

1. Зафиксировать исходный срез `main` и отдельные рабочие изменения.
2. Построить независимые списки объектов из раздела 2; сопоставить с существующими материалами.
3. Дополнить отсутствующие карточки и связи; классифицировать Graphify omissions, dynamic dispatch и внешние границы.
4. Составить полную матрицу семейств сценариев и окружений, проверить данные, настройки и lifecycle.
5. Согласовать текущие документы с историей и свидетельствами; сохранить причины и отменённые решения.
6. Пройти контрольные вопросы, закрыть доступные неизвестные, опубликовать состояние каждого критерия и оставшиеся ограничения.
7. После приёмки досье перейти к совместному анализу и выбору изменений.

Этот файл — критерии приёмки досье, а не новый автоматический gate. Он хранится рядом с доказательствами и, как остальные материалы `docs/code-review/`, исключён из рекурсивного хеширования рецензий. Его наличие не увеличивает подтверждённое содержательное покрытие кода.
