## C. Браузерная часть (Chromium 152, встроенная панель)

**Честная оговорка: LCP, FCP и CLS не измерены.** Панель скрыта (`document.visibilityState = "hidden"`, сессия не открыта ни в одном окне): `paint`-события не приходят или приходят с произвольной задержкой (в одной загрузке FCP получился 23 488 мс, в остальных пусто). Значения ниже — Navigation Timing, Resource Timing и размеры ресурсов. Это не лабораторный Lighthouse, а ориентировочные значения из одной точки; TBT и long tasks получить не удалось (0 событий при скрытой панели) [C1].

Порядок: сначала десктоп (1366×850), затем mobile (375×812, Android UA), каждый раз новая навигация. Первая страница каждого сайта — «холодная» (кэш пуст), далее статика берётся из HTTP-кэша панели, поэтому **вес считается по `encodedBodySize`** (не зависит от кэша), а время — отдельно. Сторонние ресурсы без `Timing-Allow-Origin` дают нулевые размеры: у TE 13–22 из 18–27 ресурсов непрозрачны; их размеры я добрал через curl к их CDN [C2] (кроме Google GTM/GPT и ID5 — не измерены). Окно сбора — 3 с после `load`; у TE реклама грузится и дальше (аукцион Prebid), поэтому у них число запросов занижено.

### C.5 Наблюдение: редирект-петля языка и 429 (не подтверждено на чистом профиле)

В панели первый переход на `https://ru.forecasteconomy.com/` завершился `net::ERR_TOO_MANY_REDIRECTS`, затем nginx отдавал `429 Too Many Requests` на все навигации (при том что curl с того же IP получал 200). В cookie панели обнаружены конфликтующие `fe_locale_pref=en` и `fe_locale_pref=ru` (на apex и на ru-хосте). Проверка curl [A5]: `ru.forecasteconomy.com` с `Cookie: fe_locale_pref=en` → 307 на apex; `forecasteconomy.com` → 307 на ru-хост по `Accept-Language: ru`. После удаления cookie страницы открылись. **Вывод:** при разных значениях языка на двух хостах получается пинг-понг редиректов; `limit_req ssr` (5 r/s, burst 15) затем возвращает 429. **Не подтверждено**: воспроизведение на чистом профиле, срок жизни cookie, доля реальных пользователей в такой ситуации. Стоит проверить логику установки `fe_locale_pref` (host-only и domain-cookie).

## Что у нас хуже всего и конкретная причина

Упорядочено по влиянию на пользователя и на нагрузку.

1. **Тяжёлый первичный JS и веер запросов на индикаторе.** ИПЦ: 64 запроса, 38 JS-файлов, 471 КБ gzip / 1,7 МБ после распаковки; roschart — 10 КБ / 31 КБ собственного JS, TE — 343 КБ собственного (без рекламной части). Крупнейшие куски: `main-*.js` 186 КБ gz (640 КБ распаковано), `charts-*.js` 123 КБ gz (429 КБ), `WorldMap` 57 КБ, `animation` 27 КБ, `query` 25 КБ [C1]. По `frontend/package.json` в зависимостях есть `@sentry/react`, `@rrweb/record`, `echarts`, `recharts`, `gsap`, `three`; какие из них лежат в initial-chunk, без source map не установить (**не подтверждено**; локальная сборка `frontend/dist` — более новая, `main-D1UfsbEy.js` 741 КБ, не прод). На странице региона (183 КБ HTML с контентом) браузер всё равно тянет 20 чанков (277 КБ gz). **Эффект на CPU телефона не измерен.**
2. **Hero-PNG на странице индикатора: 235 КБ (десктоп) и 306 КБ (мобильный portrait)** — это 24 % (десктоп) и 28 % (мобильный) веса страницы и в 5–6 раз больше всего HTML+CSS вместе взятых. Тег `<link rel="preload" as="image" href="/og/russia/cpi.png" fetchpriority="high">`: тот же файл служит og:image. Формат PNG, а не WebP/AVIF/SVG [C1]. Побочно: `HEAD /og/russia/cpi.png` → 405 [A8].
3. **HTML нельзя кэшировать:** `Cache-Control: no-cache, no-store, must-revalidate` на всех SSR-страницах и `Set-Cookie: fe_bind` (`Domain=.forecasteconomy.com`) на каждом ответе. Для anonymous-страниц это закрывает путь к CDN/микрокэшу: 100 % обращений идут на единственный сервер с 4 vCPU. У TE те же страницы кэшируются на CloudFront (`s-maxage` 10–60 с, `Age` до 207 с, «Hit from cloudfront»). При этом сам сервер быстр (ожидание 18–39 мс, `If-None-Match` → 304 за 0,24 с), то есть потенциал есть, мешает политика заголовков (вывод).
4. **Время до первого байта 2× хуже конкурентов из этой точки:** TTFB 542 мс против 270–278; причина — TLS-рукопожатие 483 мс против 73–101 мс (серверное ожидание, наоборот, лучшее). Контроль (timeweb.ru, тот же AS) 0,53–0,75 с → путь/хостинг; **не подтверждено для РФ**: нужна проба из Москвы без VPN. Один IPv4 без AAAA; HTTP/3 объявлен, но curl и большинство загрузок панели шли по h2.
5. **Сжатие gzip вместо brotli.** При `Accept-Encoding: br, zstd` и HTML, и JS приходят в gzip. Оценка (вывод, локально): у локальной сборки `main-D1UfsbEy.js` gzip-9 даёт 216 КБ, br-11 173 КБ (−20 %); на ~510 КБ первичного JS и CSS это ~80–100 КБ на холодный визит. Для HTML выигрыш мал (1–2 КБ).
6. **Хаб `/russia` почти пуст в сыром HTML:** 561 знак, 0 цифр, 11 уникальных ссылок (у roschart аналог 13,5 тыс. знаков и 79 ссылок; у TE `/russia` тоже оболочка без H1). Региональная страница богата текстом, но размечена только `BreadcrumbList` (у ИПЦ есть `Dataset`+`FAQPage`); title региона без значений (у roschart значение стоит в заголовках страниц показателей региона).
7. **Редирект-петля языка и 429** (см. C.5): конфликт `fe_locale_pref` между apex и ru-хостом; не подтверждено на чистом профиле.
8. **Мелочи:** шарды sitemap с первого запроса ~7 с (2 из 3); `X-Robots-Tag` приходит дважды на 404 для `/Russia/…`; `/Russia/…` отдаёт 404 вместо 301; apex по языку отдаёт 307 (временный, не кэшируется); 404-страница весит 15,7 КБ без сжатия (у roschart 2,5 КБ); `HEAD` на `/og/*.png` → 405.

### Что у нас лучше всего (по измерениям)

Серверное время ответа 18–39 мс (лучшее из трёх); HTML в 2–5 раз легче TE и в 1,5–2,5 раза легче roschart на 3 из 4 страниц; корректный 404 (`noindex`) на всех вложенных путях; единственный сайт с HSTS (preload), CSP, nosniff; `immutable`-кэш статики на год и 304; один сторонний трекер; самая полная разметка (hreflang на всех страницах, `Dataset`+`FAQPage`+`BreadcrumbList`, OG); sitemap на порядок-два больше, с содержательным `lastmod`.

## Ограничения методики

- **Одна точка и один день.** VPN-выход во Франкфурте (AS197462), ноутбук физически в МСК. Трафик пользователей РФ другой; наш сервер в Москве, поэтому для РФ-аудитории (по заметкам ~82 % РФ) задержка может быть иной в лучшую сторону (не проверено).
- **TCP-connect и DNS не сопоставимы:** локальный TUN-терминатор отдаёт connect ≈ 3–8 мс, DNS кэширован; сетевую задержку несёт TLS-время. «Ожидание сервера» (TTFB − TLS) содержит один RTT.
- **Выбросы 1,8–6,3 с** у всех трёх сайтов — шум туннеля; 5 замеров на страницу дают оценку, не распределение. p90 по сводным выборкам (n = 15–20).
- **Прямой маршрут:** внутри песочницы Claude весь трафик идёт через локальный прокси (DNS 0,02 мс, connect 0,4 мс — это прокси), поэтому curl выполнялся с `--noproxy '*'` вне песочницы (через штатный запрос на отключение песочницы для этих команд) [A1].
- **Браузерная панель скрыта:** LCP, FCP, CLS, TBT, long tasks недостоверны или отсутствуют; не измерены. Вес считался по `encodedBodySize`; у TE 13–22 ресурсов непрозрачны (нет TAO), размеры добраны curl, Google-часть (gtag.js, gpt.js) и ID5 не измерены — оценка TE — нижняя граница. Окно сбора 3 с после `load`.
- **Кэш браузера:** «холодна» только первая страница каждого сайта; mobile-загрузки идут при тёплом HTTP-кэше. Для сравнения весов использован `encodedBodySize`, для времени — медианы mobile.
- **Состояние профиля панели** содержало следы прежнего использования нашего сайта (consent, localStorage, cookie языка); cookie `fe_locale_pref` удалены, остальное не трогалось. Метрика у нас грузится по умолчанию (по `consent.js`), то есть для нового посетителя картина та же.
- **Пользовательский агент curl** честно обозначен (`techbench/1.0`), не Chrome; у нашего сайта и конкурентов могут быть иные ответы для «человеческих» UA (не проверялось).
- **Выборки малы:** 10 URL из sitemap и 1 проба на тип редиректа; отсутствие ошибок не доказывает отсутствие проблем.
- **Не оценивались:** контраст, размер тач-целей, JS-ошибки, конверсия, нагрузка на сервер, данные индикаторов, содержимое OpenAPI и MCP (по `robots.txt`/заметке 2026-10-04 не запрашивались).
- **Без изменений репозитория**, кроме этого файла; без commit/push; к продакшену по ssh не обращался.
