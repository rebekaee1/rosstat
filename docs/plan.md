План — что доделать

Этот файл — рабочий список того, что мы запланировали, но ещё не сделали. Без приоритетов и форм. Минимум описания на пункт. По мере того как пункты закрываются — они отсюда удаляются. Когда возникает новая идея — она дописывается сюда же в конец.

Last updated: 2026-05-22 (после ревизии «ты уверен в данных?»).

---

Расширить view-mode families на остальные индикаторы.

Сейчас унифицированы только trade (Phase 1), labour (Phase 2), housing (Phase 3), rates rename (Phase 4) и daily aggregation (Phase 5). Осталось пройтись по GDP, PPI, CPI, retail, banking, инвестициям. Для каждой группы решить отдельно: применим ли вообще view-mode подход (один indicator с режимами) или у группы своя внутренняя логика (например GDP nominal vs real vs by-industry — это вообще разные ряды, view-mode здесь будет вредом). Сначала аудит, потом перенос. Аудит делать в отдельной сессии, по одной группе за раз, с показом локально перед коммитом.

Реальный source-depth audit для всех 109 индикаторов.

Прошлись только по wages, key-rate, GDP, housing. Остальные 105 — не проверены на full-depth. Нужно для каждого сравнить `MIN(date)` в БД с публичной глубиной источника (Росстат архивный сборник, ЦБ исторический ряд, Минфин). Где разрыв — заводить `<name>_historical.py` immutable seed по схеме wages_historical.py. Особое внимание: ipi, retail-trade, инфляция базовая и продовольственная, инвестиции в основной капитал, строительство.

SEO-блоки для топ-30 индикаторов по показам.

Сейчас seo_blocks заполнен на около 20 индикаторах. Остальные показывают только generic-описание. Нужно для топ-30 по трафику (взять из Yandex Metrika через MCP) написать пять-семь содержательных блоков на каждый: что такое, как считается, исторический контекст, последние события, прогноз, связи с другими индикаторами. Шаблон уже есть в `backend/app/data/indicator_seo.py`.

Search keywords ревизия.

Search теперь ищет по `seo_keywords` — но качество корней на индикаторах разное. Где-то полный список синонимов (cpi: «инфляция, ИПЦ, рост цен»), где-то только пустые SEO-шаблоны («Зарплаты (изм. г/г) Россия, Зарплаты (изм. г/г) прогноз»). Пройтись по 109 индикаторам, добавить осмысленные корни на русском и английском. После этого посмотреть метрику «пустых поисков» — где пользователь ищет, но ничего не находит.

Аудит других backfilled индикаторов на annual-in-monthly trap.

Wages найден и фикснут (24 годовые точки переехали в wages-nominal-annual). Возможно тот же трап есть на других индикаторах, куда я добавлял исторические данные: key-rate (там события, не monthly — но проверить как frontend label показывает), housing-price-primary/secondary (там quarterly bo и quarterly история — ОК), gdp-real (там quarterly, есть Q1-Q4 — ОК). Скорее всего trap только на wages, но нужна явная проверка с SQL: `SELECT code, frequency, MIN(date), MAX(date) FROM ...`.

Telegram-бот.

Был задуман модуль, не начат. Подписка на индикатор, daily push с изменениями, кастомные алерты. Из инфраструктуры — нужен webhook URL, доступ к API через BOT_TOKEN, отдельная таблица в БД для подписок. Архитектурно — отдельный сервис в docker-compose, не часть backend.

Embed-виджеты.

Embed-виджет для индикатора (iframe + чистая SVG-карточка для медиа) — был в roadmap. Скелет URL `/embed/<code>` есть в backend. Нужно: дизайн виджета, CSP для iframe-allowed origins, копи-кнопка кода вставки на странице индикатора.

Календарь публикаций — UI.

Backend часть готова: 1208 событий, 46 source codes, `bad_public_rows=0`. UI-страница «Календарь» либо отсутствует, либо плоская. Нужно: цветная разметка по категориям, фильтр по источнику, push «через 24 часа выйдет ключевая ставка».
